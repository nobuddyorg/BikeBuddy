# BikeBuddy review: lead report

- **Scope:** the whole repository at `main` = `b0bde68` (2026-09-24). Vendored code (`frontend/src/vendor/`), lockfiles and generated output were skipped. **No source files were modified**; this review only adds `REVIEW.md` and `reviews/`.
- **Context (inferred, because the request's context line was left as a template):** BikeBuddy is a public ride-log app. It has a static frontend on GitHub Pages (`nobuddy.org/BikeBuddy`), an API on Azure Functions Flex (Node 24), Cosmos DB Serverless and Blob Storage, and sign-in through Entra External ID with self-service sign-up. The user base is small (a hobby community) and there is one maintainer. The data is sensitive: GPS tracks and geotagged photos. Severities below are calibrated to that deployment.
- **Raw reviewer output:** [`reviews/security-reviewer.md`](reviews/security-reviewer.md), [`reviews/performance-reviewer.md`](reviews/performance-reviewer.md), [`reviews/qa-reviewer.md`](reviews/qa-reviewer.md), [`reviews/architecture-reviewer.md`](reviews/architecture-reviewer.md), [`reviews/ops-reviewer.md`](reviews/ops-reviewer.md), plus the extra cross-lens pass in [`reviews/completeness-critic.md`](reviews/completeness-critic.md).

## Executive summary

BikeBuddy's core security design holds up under adversarial checking. Every data endpoint authenticates in code, and every Cosmos read uses the token's `sub` as the partition key, so **no reviewer, verifier or the completeness critic found a cross-user access path**. User content is rendered with `textContent` under a `script-src 'self'` CSP. Upload parsing resists XXE, entity expansion, deep nesting and decompression bombs (probed). Nothing rated critical. After deduplicating **167 raw findings into 51**, there is **1 high, 24 medium and 26 low**.

- **One exploitable outage (high, R-01).** Anyone, with no account, can make every signed-in request return HTTP 500 by sending about 10 junk tokens per minute per instance: they drain the JWKS rate limiter. The lead reproduced it. The fix is small and local to `authMiddleware.js`.
- **Operations is the weakest area.** Production has no telemetry or alerting (R-06). There are no backups beyond an 8-hour periodic Cosmos default and no destroy guards on `-auto-approve` applies (R-03, R-04). Production has silently missed the last 11 merges to `main`, because bot merges trigger no workflows (R-02). The auth switch fails open when configuration is missing (R-05). Each is medium on its own, but together they mean an incident would be noticed late and data loss could be permanent.
- **The privacy lifecycle does not match what the UI promises.** Deleting a tour keeps its photos (R-09). Account deletion can orphan data with no owner (R-10). The export leaves out the GPX files and photos (R-11). There is no privacy notice (R-12). This matters because the app's entire content is location data.
- **Abuse and cost are unbounded.** Anyone can sign up, and there are no quotas, no rate limits, and no memory-bounded upload limit (R-07, R-08).
- **Correctness bugs users will actually hit.** A numeric GPX name permanently breaks that tour's detail view (R-15). The profile name is overwritten on every load (R-16). Multi-segment stats include the gaps (R-17). Empty or route-only GPX files are stored as 0 km tours (R-18). Returning users run a stale frontend (R-13). There is no re-login on token expiry (R-20). Undo-deletes are lost when the tab closes (R-21).
- **Test suites are strong on the backend but have blind spots.** The backend has 288 tests at 99.85% statement coverage plus mutation testing. But `ui/*` is untested, and no integration or e2e test ever uses two users (R-25).

**Bottom line:** fix R-01 now. Before new features, put the operational safety net in place: items 2 to 5 of the [top 10](#top-10-fixes-in-order) are mostly small configuration changes that make every other failure recoverable and visible.

## How this review was done

1. **Five specialist reviewers** (security, performance, QA, architecture, ops) each covered the whole repo in **two independent passes**. The second pass hunted for issues the first had missed and disputed first-pass claims it found wrong. The reviewers ran the unit tests, `npm audit`, and throwaway probe scripts against the real modules.
2. **A completeness critic** received all five reviewers' findings and looked for what fell between the lenses. It added 7 findings (`LEAD-Gnn`).
3. **Adversarial verification.** Each of the 9 findings a reviewer rated high got two independent verifiers told to refute it: one checking whether the code really behaves as claimed (with a reproduction where feasible), one calibrating real-world impact. Every medium or low finding got a skeptical batch check. No reviewer rated anything critical.
4. **Lead re-verification.** I re-read the code for all 9 high findings. I reproduced SEC-01 (JWKS exhaustion) and PERF-01 (the map budget blow-up) myself, plus the GPX-name `TypeError` (R-15) and the `Math.min` overflow (R-38). I checked the Actions run history for the deploy drift (R-02). An automated check of all 167 cited `file:line` pairs found 4 wrong line numbers; they are corrected here and annotated in the raw files.
5. **Not run:** Playwright/e2e, Stryker, OpenTofu, and anything needing Azure credentials. Branch-protection settings and the live Azure configuration could not be observed; statements about them are marked as inferred.
6. **Baseline:** functions 288/288 tests pass (99.85% statements, 99.73% branches); frontend 167/167 pass; `npm audit --omit=dev` reports 0 vulnerabilities.

## Contradictions between reviewers, and how they were resolved

1. **Do auto-merged Dependabot PRs deploy unverified code (OPS-01, SEC-03), or never deploy at all (OPS-G01)?** I checked both claims against the Actions run history. Auto-merge waits for required checks (commit 75321d9: branch protection requires CI), so failing code is not merged automatically. But a merge made with `GITHUB_TOKEN` starts no workflows: the last Deploy is run #249 on 2026-09-03, and 11 bot merges since then are on `main` but not in production. **Decision:** the real risk is silent drift (R-02, medium). Ungated deploys (R-23) are a separate medium with lower likelihood.
2. **SEC-01: high (reviewer, code-truth verifier) or medium (impact verifier)?** Kept **high**. The impact verifier's mitigations are real: a warm instance keeps its cached key for up to 10 minutes, and the outage stops when the attack stops. But the attack needs no account, no victim interaction and only about 10 requests per minute per instance, and it defeats Flex scale-out because every new instance starts cold. That is a realistic outage path, not a theoretical one.
3. **PERF-01: does the map budget bound nothing, or only fail for long tours?** The verifier was right. 60 km tours still shrink (1M to 323k points), and zero reduction happens only for long tours. It also showed that most of the CPU goes to the 13-pass Douglas-Peucker search, not the gap rule. **Decision:** medium. Dropping the gap rule alone would fix the payload size but not the latency; the real fix is an overview track precomputed at upload (R-14).
4. **OPS-02: is there really a one-click destroy?** The second pass was right that `destroy.yml` cannot run today (it passes an undeclared `package_path` variable), so that path is dormant. The auto-apply replacement risk is live. **Decision:** medium (R-04). Put `destroy.yml` behind an approval before anyone fixes the variable.
5. **Fail-open auth: low (SEC-04), medium (OPS-06, ARCH-05) or high (second-pass dispute)?** The dispute found a documented trigger: the manual `tofu apply` in `docs/how-to/infrastructure.md` passes no Entra variables. Existing users' data stays unreachable, because it is partitioned by their real `sub`. The exposure is data created under the shared dev identity while the window is open. **Decision:** medium (R-05).
6. **GPX-name bypass: a security issue (SEC-07, medium) or a correctness issue (verifiers, low)?** There is no HTML sink (everything renders via `textContent`), so it is not XSS. But the lead reproduced a permanent HTTP 500 from `GetTour` for a plain numeric name, which is a realistic input. **Decision:** medium, filed as correctness (R-15).
7. **Photos kept after tour deletion: high (QA-01, ARCH-02) or medium (all four verifiers)?** The container is private, and no SAS link can be minted without the tour document, so nothing is exposed. **Decision:** medium; the erasure the user asked for is not carried out (R-09).
8. **`Math.min` overflow: medium (PERF-04, QA-05) or low (verifier)?** The lead reproduction fails at about 150k elevation points, around 8 MB of compact track points. Typical device exports, which include time and extensions, hit the 10 MB cap first. **Decision:** low, but it is a one-line fix (R-38).
9. **Missing Application Insights: low (PERF-16) or medium (OPS-04)?** Having no production telemetry at all is an operations gap, not a performance detail. **Decision:** medium (R-06).
10. **Container drift: medium (ARCH-04) or low (second pass)?** It has no functional or security consequence today. **Decision:** low (R-34).
11. **OPS-10: was the deploy tool broken for a month?** Refuted by the run history: Deploy #249 installed core tools and published successfully. What remains, an unpinned install inside a privileged job, is part of R-22.
12. **Date editor off by one: medium (QA-09, batch) or lower?** It only affects rides that start within the UTC offset of midnight, and the audience is mostly European. **Decision:** low (R-43).
13. **Deep-link `URIError`: medium (QA-07) or low (second pass)?** It needs a hand-crafted or corrupted link. **Decision:** low (R-44).

## Top 10 fixes, in order

The order weighs severity and likelihood against effort and dependencies: the safety net goes before the riskier changes. Effort: S = under a day, M = a few days.

1. **Close the JWKS outage path** (R-01, R-27; effort S). Resolve keys from a locally held JWKS that is refreshed on a timer, or use `getSigningKeys()` with a long max age. Treat an unknown `kid` and `JwksRateLimitError` as 401, allowing at most one forced refresh every few minutes. Rebuild the client when `jwks_uri` changes, add a timeout to the metadata fetch, and serve the cached metadata when a refresh fails. Add a unit test that sends junk-kid tokens and then a valid one. _First because it is the only high finding, it needs no account to exploit, and the change is confined to one file._
2. **Put a safety net under user data** (R-03, R-04, R-24; effort S-M). Turn on Cosmos continuous backup (`Continuous7Days`), blob soft delete (for example 14 days), container soft delete and versioning. Add `prevent_destroy` and a `CanNotDelete` lock on the resource group or data resources. Make deploy run `tofu plan` and fail when the plan deletes or replaces anything. Put `destroy.yml` behind a protected environment with a typed confirmation. Make the full-stack e2e cleanup refuse any non-localhost Cosmos endpoint. Write a short restore runbook. _This comes before any other infrastructure change, because it makes every later mistake recoverable._
3. **Make auth fail closed** (R-05; effort S). Make `SKIP_AUTH` an explicit variable that defaults to `"false"` and is never derived from empty inputs. Have `provision.sh` refuse to apply when the Entra variables are empty unless an explicit dev flag is set, and fix the bare `tofu apply` in `docs/how-to/infrastructure.md`.
4. **Make `main` and production the same thing** (R-02, R-23; effort S-M). Have auto-merge use a GitHub App token (or dispatch Deploy after merging) so the gate and Deploy actually run. Limit auto-merge to patch and minor updates via `dependabot/fetch-metadata`. Trigger Deploy from `workflow_run` on a successful gate and restrict `workflow_dispatch` to `main`. Deploy the frontend only after the Functions publish succeeds, and add an `/api/health` smoke test. Run one manual deploy now to ship the 11 pending merges.
5. **Turn on telemetry and alerting** (R-06; effort S-M). Provision Application Insights with a daily ingestion cap and set `APPLICATIONINSIGHTS_CONNECTION_STRING`. Alert on the 5xx rate and on auth failures (either would have caught R-01), add an availability test on `/api/health`, and send a notification when a scheduled deletion run fails. Correct the claim in the cost report.
6. **Bound abuse and cost** (R-07, R-08; effort M). Enable `app.setup({ enableHttpStream: true })` so busboy's limit also bounds memory. Enforce per-user quotas (tour count, total bytes) in UploadTour and UploadImage, add per-user rate limiting, and lower `maximum_instance_count`. Consider an automated budget action instead of email only.
7. **Make delete and export do what they promise** (R-09, R-10, R-11, R-12; effort M). DeleteTour should also remove the `${userId}/${tourId}/` image prefix, with a one-off reconciliation for existing orphans. The deletion queue should store `{oid, sub}`, and the job should re-run the purge before it deletes the identity. GetMe and UpdateProfile should refuse to recreate an account that has a pending deletion. The export should include the GPX files and photos (SAS links or a zip). Publish a privacy notice covering the controller, legal basis, retention and recipients (Microsoft, CARTO).
8. **Least-privilege CI credentials** (R-22; effort M). Replace the client secret with OIDC federated credentials. Scope the subscription-wide Contributor principal down to the resource group, and scope the `ARM_*` environment to the infrastructure job only. Pin `azure-functions-core-tools` to the version the gate already uses. In the deletion job, run `npm ci` before `azure/login`.
9. **Fix the backend correctness bundle** (R-15 to R-19, R-38; effort S each). Coerce GPX-derived names with `String()` and run them through `nameSchema` (or set `parseTagValue: false` for text nodes). Stop GetMe overwriting a name the user set. Compute distance and moving time per segment. Return a clear 400 for empty or `<rte>`-only files, or parse routes. Clear the cached container promise when it rejects. Replace `Math.min(...)` / `Math.max(...)` with a loop. Give each fix a regression test.
10. **Stop shipping a stale frontend** (R-13; effort S). Stamp `CACHE_NAME` with the commit SHA in the deploy step (next to `generate-config`). Make same-origin JS, CSS and `config.js` stale-while-revalidate or network-first, and keep cache-first only for `vendor/` and icons.

**Next after the top 10:** R-14 (precompute a map overview track at upload and enforce the point budget as a hard cap), R-20 and R-21 (re-login on 401; send deletes immediately and keep undo on the server or use `keepalive`), R-25 (two-user integration tests with real JWTs against the emulator, and coverage for `ui/*`), then the low findings, grouped by file.

## What is already good (confirmed, not just claimed)

- Ownership is enforced by construction: every read or query passes the token-derived `sub` as the Cosmos partition key, queries are parameterised, route ids must be UUIDs, and blob names are built on the server. No reviewer, verifier or the critic found an IDOR.
- JWT validation pins RS256, reads the issuer from OIDC metadata and checks the audience. Client token faults become 401 while infrastructure faults become 5xx, and logs never contain tokens or claims.
- Upload hardening: streaming busboy limits, magic-byte checks, sharp `limitInputPixels`, and EXIF (including GPS) stripped by the re-encode. The installed fast-xml-parser 5.11.1 rejects XXE, `__proto__` tags and deep nesting, and does not expand nested entities (lead and reviewer probes).
- The frontend never renders user data through an HTML sink, and the service worker never caches API responses or SAS URLs.
- CI hygiene is above average: SHA-pinned actions, `persist-credentials: false`, minimal default permissions, zizmor, CodeQL and OpenGrep, and the privileged Graph credential is kept out of the public API.
- Code comments explain the trade-offs (write ordering, ETag retries, why a patch rather than a replace), which made verification fast. Most findings are about what surrounds the code, not the core logic.
